# CICS version of the online screens (untested)

> **Not tested.** There is no CICS (or z/OS) in this environment, so these
> programs have never run. `./check.sh` compiles everything *around* the
> `EXEC CICS` commands with GnuCOBOL (copybooks, data names, logic), which
> catches most mistakes, but only a real CICS translator can prove the
> commands themselves.

The GnuCOBOL menu (`bin/bankmain`) asks one question at a time. On a
mainframe the same work is done with full-screen 3270 maps and
**pseudo-conversational** programs: each program sends a screen, ends the
task with `RETURN TRANSID(...) COMMAREA(...)`, and is started again when the
user presses a key. Nothing waits in memory while the user is typing; the
state travels in the COMMAREA (`copy/CBCOMM.cpy`).

| Transaction | Program | Map | Does |
|---|---|---|---|
| CBSN | CBSIGN | CBSNMS | Sign-on through the security manager (`EXEC CICS SIGNON`) |
| CBMN | CBMENU | CBMNMS | Menu, XCTL to the chosen function, PF3 signs off |
| CBAI | CBINQ  | CBAIMS | Account inquiry + last 5 transactions (AIX browse, newest first) |
| CBFT | CBXFR  | CBFTMS | Two-step transfer: validate and show names, then confirm with Y |

Points worth noticing in CBXFR:

* the confirm step refuses if the screen was changed after validation;
* both accounts are read for UPDATE in account-number order, so two
  opposite transfers cannot deadlock;
* balances are re-checked under the lock, and everything is one unit of
  work (`SYNCPOINT` / `SYNCPOINT ROLLBACK`);
* same available-balance rule as the batch `ACCTPOST`.

Files

* `maps/*.bms` - BMS map sources, generated by `maps/genmaps.py` (which
  also writes the symbolic maps in `copy/`, so the two cannot drift apart)
* `src/*.cbl` - the programs
* `CSD.txt` - DFHCSDUP definitions (transactions, programs, mapsets, files)
* `../jcl/CICSFILE.jcl` - TRANLOG as an ESDS with an alternate index on the
  account number
* `stub/` - minimal stand-ins for IBM's DFHAID, DFHBMSCA and the EIB, used
  only by `check.sh`
